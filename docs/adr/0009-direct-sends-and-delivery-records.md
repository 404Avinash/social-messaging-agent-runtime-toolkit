# ADR-0009: Tools send when called; the toolkit records every message it delivers

| Status | Date | Deciders |
|---|---|---|
| Proposed | 2026-10-16 | SMART maintainers |

## Context

[ADR-0002](0002-in-band-sends-through-notify-context.md) queues every message a tool sends during an agent turn, so that no assistant event lands in AgentCore Memory between a `toolUse` and its `toolResult`. That corruption comes from the mid-turn memory write, not from the send: a `notify` call outside the context reaches the notification Lambda with `log_to_memory=False` and writes nothing. What the queue adds is delivery order, a recipient pinned by the webhook, and one place that turns S3 links into media ids. What it costs is larger. A queued message reaches the user only after the agent's last model call, and with a thinking model every model call after the tool takes seconds. A tool's "sent" means "queued". A turn that raises drops the queue, and the `personal-assistant` scheduled turn never delivers it. Queued messages are never written to memory (the open question in [ADR-0006](0006-memory-ownership.md)), so `_history.py` rebuilds them on restore from tool inputs: button and list options are lost, and a template sent by a tool disappears. Developers learn two send paths, the queue and `immediate=True`, with different recipient and memory rules.

The constraints that stay: WhatsApp does not guarantee the order of messages sent back to back, so consecutive sends stay `outbound_gap_seconds` apart. The toolkit is framework-agnostic, so the design may rely on no framework hook and on nothing a tool returns. The two runtime layers never import each other ([ADR-0001](0001-two-runtime-layers.md)), and the runtime is vendored ([ADR-0003](0003-agent-runtime-is-vendored.md)), so projects keep returning `outbound_messages` until their copy is replaced.

## Decision

There is one send path. `notify.send_text`, `send_message` and `send_template` deliver when called: they invoke the notification Lambda synchronously (`RequestResponse`), which sends, refreshes the typing indicator and returns a delivery receipt (`wamid`, `sent_at`, and the message rendered as text: a template through the registry the Lambda already uses for memory, any other message through a new renderer). Inside `socialagent_notify_context()` the recipient is always the invocation's sender, consecutive sends are paced `outbound_gap_seconds` apart, and the receipts are returned in `SocialAgentResponse.delivered`.

The agent's framework still owns the conversation inside the loop: user turns, replies and tool exchanges, written by its session manager or by the developer through `create_memory_client`. The toolkit writes every message it delivers, exactly once and always as the assistant: a send outside an agent turn is written by the Lambda that sent it; a send during a turn is written after the turn returns, by whoever invoked the runtime (the webhook, or a handler through the same shared helper). Nothing writes memory while a turn runs, no tool returns or logs what it sent, and the toolkit retries nothing that can repeat work: it runs each turn once and attempts each send once.

Question for the maintainers: accept the single send path, including the webhook writing delivery records to memory?

## Alternatives considered

- **Keep the queue (ADR-0002).** Keeps every cost listed under Context, the latency first.
- **Two modes behind a flag (`queued | direct`).** Two paths to document, test and reason about, which is the problem this record removes. Rejected.
- **Direct asynchronous sends** (`InvocationType="Event"`, what `immediate=True` does today). Two sends run in parallel Lambdas with no order, and the tool learns nothing about delivery. Rejected.
- **The tool returns the receipt as its `toolResult`, and restore reads it there.** Every tool author would have to return it. Rejected.
- **A framework hook adds the receipt to the tool result** (Strands' `AfterToolCallEvent`). Framework-specific. Rejected.
- **The runtime writes the receipts when the context closes.** It would cover every invoker and a webhook that timed out, but needs a second memory writer in the runtime package, because ADR-0001 forbids importing `writer.py`. Rejected for one writer in the Lambda layer.
- **Idempotency keys in the state table, so retries are safe.** Makes the state table mandatory. Rejected for not retrying.
- **An idempotency key the notification Lambda and the provider honour.** The provider cannot: EUM Social's `SendWhatsAppMessage` takes only `originationPhoneNumberId`, `message` and `metaApiVersion` (botocore's `socialmessaging` 2024-01-01 model), so no token reaches WhatsApp. Only the Lambda could deduplicate, and that needs storage shared across invocations, the state table again. Rejected for not retrying.

## Consequences

- **Latency.** A message arrives when its tool runs, ahead of the model calls that follow it; typing is refreshed after each send, though it still lapses about 25 seconds after the last one. Each send adds one synchronous Lambda round trip to the turn, unmeasured.
- **Pacing moves, it does not grow.** The gap moves from the webhook's drain to a per-invocation lock in `notify`; the lock is needed because Strands runs tool calls concurrently. The webhook waits out what is left of the gap before the final text, and an empty final text after a delivery is a complete reply. Tool messages arrive earlier than with the queue; the final text can arrive later, by the sends' round trips.
- **Failures are visible.** A failed send is a tool error the agent can handle. A turn that raises after a send leaves the user with what was delivered, then the error text, and the runtime returns the receipts collected so far, which are written.
- **Restore holds the real content.** Receipts are assistant events with the rendered text, so options and template wording survive restore. A receipt stamped with `sent_at` sorts between its tool's `toolUse` and `toolResult`, the shape ADR-0002 exists to prevent, so what keeps restore valid is the restore filter (`REPLAY_UNSAFE_BLOCKS` in `_history.py`), not when the receipt is written: every session manager that reads this memory must apply it. `_history.py` drops tool-only turns and keeps the tool-input fallback only for history without receipts. A manual-memory integration stops logging what its tools send, and reads the receipts through `get_turns` as plain text (the unwrapping is a separate change, independent of this record).
- **No retries, at seven places.** Two invariants rest on the toolkit never repeating work that may already have happened: it runs each turn once, and sends each message at most once. Neither covers an SNS redelivery, which the webhook does not deduplicate (a project guards with `state.claim_once`), a repeated delivery of a schedule's firing, which the scheduler Lambda, and the notification Lambda for a schedule's built-in send, skip only with the state table on (each records the firing by schedule id and due time before running it), or an agent that sends a message again. Seven retry paths can break them, and each is closed:
  - Turn: the webhook Lambda's async retries (2 by default). Closed: `aws_lambda_function_event_invoke_config.webhook` (`infra-terraform/modules/lambdas/main.tf`) sets `maximum_retry_attempts = 0`.
  - Turn: SQS redelivery of a buffered flush. Today a flush whose `clear_flushed` fails after the reply, or whose webhook times out or crashes before the `finally` that clears it, comes back after the 150s visibility timeout, up to 5 receives, and `should_flush` runs the same snapshot again (the comment in `_handle_flush` names the duplicate). The fix is a flush that claims its snapshot with a conditional write before it invokes the runtime, so a redelivery finds nothing to run and a flush that dies loses its reply instead.
  - Turn: botocore's own retries on `invoke_agent_runtime`, which the Lambda setting does not reach. Closed for the webhook. Checked against botocore 1.43.102: the client `webhook.py` built had no `Config`, so it ran in legacy mode with 5 attempts and a 60s read timeout, and legacy mode retries a `ReadTimeoutError`, a closed connection and a 5xx (`GENERAL_CONNECTION_ERROR` in `botocore/retryhandler.py`, the status codes in `botocore/data/_retry.json`). A turn that returned nothing for 60 seconds was invoked a second time before the webhook's 120s timeout; the queue hid only the duplicate messages, because the first attempt's response was discarded, and the second invocation repeated the tools' effects (schedules, state, `immediate` sends). The call is now in `src/socialagent/handlers/runtime_call.py`, whose `RUNTIME_CLIENT_CONFIG` sets `retries={"total_max_attempts": 1}` and a 5s connect timeout, with a read timeout that ends 15s before the Lambda does. It must be `total_max_attempts`: in `Config`, `max_attempts` counts retries only, so `max_attempts=1` resolves to `total_max_attempts: 2`, two invocations. `call_runtime` tries again only a call that AgentCore throttled or that never connected, since neither ran the turn; a 5xx or a dropped connection is not tried again. The scheduled `invoke_agent` in `personal-assistant` goes through `call_runtime` as well.
  - Send: botocore's retries on the `Invoke` from the runtime's `notify` to the notification Lambda, synchronous under this record. `notify._lambda_client()` builds `boto3.client("lambda")` with no `Config` (connect and read timeouts of 60s, legacy retries), and today's `Event` sends and `upload_media` already go through it, so a response lost after the Lambda has accepted or delivered invokes it again and sends the message twice. Lambda itself never retries a synchronous invoke. The fix is the same single attempt, with a read timeout longer than the notification Lambda's own timeout (60s): the client never gives up while the Lambda is still working, and a hung Lambda ends at its timeout and comes back as a `FunctionError`, not as a retry. The admin console's `RequestResponse` send to the same Lambda also uses a client without `Config`, and takes the single attempt, bounded by its own 30s Lambda timeout rather than a longer read timeout.
  - Send: botocore's retries on `SendWhatsAppMessage`, inside the notification Lambda. `EUMSocialProvider` builds its `socialmessaging` client with no `Config`, so a response lost after EUM Social accepted the message sends it again. This path exists today for every send, out-of-band ones included. The fix is a single attempt with a read timeout inside the notification Lambda's timeout. It is the only `socialmessaging` client (ADR-0001), so one change closes botocore's retry on every send; the handler and Lambda retries that wrap it are closed separately, below.
  - Send: the handlers' own resends. The webhook's `_send_response` sends the final text a second time, and the scheduled sends' `with_retry` (`handlers/scheduled.py`) makes up to 3 attempts, both on a 500 or 503 (`with_retry` also on EUM Social's `InternalServiceException` and `DependencyException`), after which the message may already be out. Both resends are removed.
  - Turn and send: the async retries of the notification, event and scheduler Lambdas (2 by default; nothing in `infra-terraform/` changes that). The notification Lambda is the schedules' target unless `enable_scheduler_lambda` is set, and it re-raises provider errors; the event and scheduler Lambdas time out at 30s. A retry can therefore resend a delivered message (`handlers/common.py` and `memory/writer.py` already say so), and a scheduled `invoke_agent` that runs past 30s runs its turn, with its direct sends, again. The fix is `maximum_retry_attempts = 0` on each one's `aws_lambda_function_event_invoke_config`.

  No retry also gives up the safe ones: a throttled `Invoke` or `SendWhatsAppMessage` (`TooManyRequestsException`, `ThrottledRequestException`) never ran, so retrying it breaks neither invariant, yet it is now reported as a failed send (see Open questions). Two of the seven, the webhook's async retries and its runtime client's, are closed; five remain, and their fixes can ship on their own, ahead of this record. The provider's fix alone makes every 429 fail on its first attempt, the webhook's final text included, because the webhook's retry markers do not match `ThrottledRequestException`; the scheduled sends' `with_retry` reads EUM Social's error codes.
- **An unknown outcome is not a failure.** With one attempt, a connection lost or timed out after the request left can mean the message was delivered. `notify` raises a distinct `DeliveryUnknown`, whose message tells the agent not to send it again, rather than the error of a send that was refused; no receipt is recorded for it. The user may then have a message that memory does not hold, the same trade-off as a webhook timeout; the toolkit does not send it twice, though an agent that ignores the error still can.
- **Failed webhook events** still reach the DLQ (M15). On the SNS path, a crashed or timed-out webhook loses that reply instead of duplicating it.
- **A webhook timeout (120s)** on the SNS path still runs the turn once, but its receipts are never written; the closing text is lost too, as it is today. Accepted: it is rare and the toolkit does not run it again.
- **The recipient pin moves to `notify`.** Inside the context a different `phone` argument is logged and the send goes to the sender, as the drain does today, so a prompt injection still cannot redirect a send; a send to another number belongs in an event or scheduler handler. Code holding the runtime role can still invoke the Lambda with any phone, as today. M28 is restated.
- **Media upload moves, it does not go away.** Converting an S3 `link` into a `media_id` moves from the webhook to the notification Lambda, so recipes keep working unchanged and the conversion sits under the notification role's IAM grants (M29) instead of a code check alone. It also fixes the broken link `immediate=True` sends today.
- **Removed:** the queue and the `outbound_messages` contract, `immediate`, `log_to_memory` and `memory_text` on `notify`, the webhook drain and its recipient override, and two Known Issues entries in `AGENTS.md`.
- **Compatibility.** The webhook keeps a reader for `outbound_messages` from older vendored runtimes and logs a deprecation warning; `SOCIALAGENT_VERSION` is bumped. History written before this change has no receipts and restores through the fallback.
- **Acceptance updates three records at once.** While this record is Proposed it replaces nothing, so its `supersedes` stays empty. `tests/test_adr_format.py` validates each record's own front matter, the index entry and its status, but not that a record's `supersedes` and the older records' `superseded_by` agree. So the change that accepts this record must, in the same commit, set this record to `Accepted` with `supersedes: [ADR-0002, ADR-0006]` and a real Enforced-by list, set ADR-0002 and ADR-0006 to `status: Superseded by ADR-0009` and `superseded_by: ADR-0009` (front matter and table), and update all three rows of the `docs/adr/README.md` index. Otherwise the index says two decisions are in force that contradict this one.
- **The webhook gets a memory writer**, for delivery records only. This reverses ADR-0006's "the webhook never writes"; out-of-band writes are unchanged.

## Open questions

- Do AgentCore Memory and the Strands session manager restore events in `eventTimestamp` order, so that a receipt stamped with `sent_at` lands before the closing text written earlier in wall-clock time? In that order it also lands between its tool's `toolUse` and `toolResult`, so the answer covers that interleaving too. The wire format carries whole seconds, so a same-second collision needs a rule either way.
- How long is a synchronous send, warm and cold? Measure a turn that ends in a menu and one with a slow tool on a deployed stack before accepting, against a time budget the record does not set yet. Two sends that reach the notification Lambda's 60s timeout already use the webhook's 120s, and after the invoke the webhook still waits out the gap, sends the final text and writes one `CreateEvent` per receipt (up to 12s each, 22s with `x-amz-retry-after`); a synchronous invoke also waits for a cold start's init, which the function timeout does not count; and the same provider runs in Lambdas of 120s, 60s and 30s, one call per chunk of a long text. Acceptance needs the webhook's, `notify`'s and the provider's read timeouts derived from that budget, with the receipt writes bounded.
- What does the webhook do when its single-attempt `invoke_agent_runtime` read timeout fires? It stops waiting for a long turn there, 15s before the Lambda timeout, and today it sends the configured `timeout` text, whose default asks the user to try again, while the turn may still be running and delivering; it writes no receipt. Acceptance needs that timeout treated as an unknown turn outcome (no generic text, or a neutral one, and no receipts), stated with the webhook-timeout consequence and tested.
- How does a turn that raises return its receipts? With the one-line blueprint change, an exception from `agent(...)` skips the `return`, so the receipts collected so far never reach the invoker. Acceptance needs that mechanism defined, with the blueprints, the `AGENTS.md` entrypoint pattern and the "receipts of a failed turn" test aligned with it.
- `DeliveryUnknown` covers only `notify`'s hop. The notification Lambda re-raises every provider error, so a `SendWhatsAppMessage` read timeout reaches `notify` as the same `FunctionError` as a refused message (today `upload_media` turns any `FunctionError` into a `RuntimeError`), and nothing classifies a 5xx (`InternalServiceException`, `DependencyException`) or a Lambda timeout after the send. Acceptance needs each outcome classified as unknown, failed or never run and carried from the provider through the Lambda to `notify` (a contract change that bumps `SOCIALAGENT_VERSION`), `DeliveryUnknown` exported from `socialagent_runtime`, and a rule for what `EventContext` does with an unknown outcome.
- Does throttling keep a retry with backoff for sends (see No retries)? The runtime call keeps one: `call_runtime` tries a throttled call again, up to three tries in all.
- A framework that restores tool inputs as text could show a send twice, once from its tool record and once from the receipt. Is a documented "do not log sends" enough?
- What enforces ADR-0002 and ADR-0006 once they are superseded? `tests/test_adr_format.py::test_cited_paths_and_symbols_exist` checks every record's Enforced-by whatever its status, so deleting `tests/test_notify_immediate.py` fails it on both records' citations; and superseding ADR-0006 whole leaves decisions still in force without a record: phone-derived session ids, the assistant-only writer, the restore filter (`strip_replay_unsafe`, which Restore relies on), monotonic timestamps and the dev-mode no-op. Acceptance needs a choice between the test skipping Superseded records and keeping the cited tests, and this record's Enforced-by repeating the decisions of both that stay.
- The legacy `outbound_messages` reader is the drain, which this record strips of its recipient pin and `_upload_media_if_needed`; an older vendored runtime still queues the `phone` the agent passed and raw S3 links, so M28 would break and its media would stop converting. Acceptance needs the reader to pin every message to the sender and use the S3-link conversion that moves to `handlers/common.py`, each with a test. When is the reader removed?
